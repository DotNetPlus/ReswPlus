Make the Native AOT sample publishable on every architecture
Three things stood between the sample and a deployable app.

Building it for anything but x64 produced a project whose generated
resource class did not exist, so the XAML compiler failed on every page
that used it. The platform an app is built for is passed down to the
projects it references, and the generator is a netstandard2.0 analyzer
that has no platform: built as x86 or ARM64 it is an assembly Roslyn
declines to load, and an analyzer that fails to load generates nothing.
Every sample now pins that reference to AnyCPU. This was not specific to
the new sample -- the existing ones were equally unbuildable for x86 and
ARM64, and are fixed with it.

Publishing produced an ordinary self-contained app rather than a native
one: the AOT compiler is brought in by the restore, so asking for it only
in the publish profile was asking too late, and the publish quietly fell
back. It is declared in the project instead, together with the runtime
identifiers it resolves against -- which is also what the earlier crash
was really about. PublishAot without RuntimeIdentifiers is what produced
an app that threw inside Windows.UI.Xaml before its first window, not
Native AOT itself, so the correction is recorded where the wrong
explanation was.

Verified by publishing all three: win-x64, win-arm64 and win-x86 each
produce a single native executable of a few megabytes with no assemblies
beside it, and the resources compiled into it.

Make the Native AOT sample actually start
The sample built, but it fail-fasted the moment it was run.

Two things were wrong. It had no launch profile, so the IDE started the raw
executable rather than the app: the crash record showed an empty faulting
package name, and UWP XAML cannot start without package identity. And the
Release configuration turned Native AOT on for an ordinary build, which
produced an executable that threw inside Windows.UI.Xaml before its first
window. Native AOT is applied when the app is published, so it now lives in
the publish profiles, next to the runtime identifier it belongs with, and
building and running the sample works in either configuration.

Verified by packaging, installing and driving the Release x64 build: the app
starts, every sample page is there, and the strings it renders are the
generated ones -- including the pluralized resource picking its singular
form for one and its plural form for ninety-nine.

Also record how to build, launch and recover this sample in repo memory, and
let the solution register the shared projects the way the IDE expects.

Build both UWP samples from the same sources
The Native AOT sample was a single page of its own, which made it a second
app to keep in step with the first rather than the same app on the other
toolchain. Move the app into a shared project both consume, so the pages,
the converters, the images and the strings exist once and the only thing
that differs between the two is the project file.

The external library the sample uses to show resources coming from another
assembly can't be shared the same way: it targets UAP, which a modern .NET
app cannot reference. It gets a second project of its own, sharing its
resources through a shared project as well, so both apps demonstrate
library resources from the very same .resw.

Fix the namespace a shared resource is generated into. The compiler hands
a linked file over the way it is written in the project, and the leading
'..' of a path reaching out of the project directory ended up in the
namespace of the generated class: a resource shared as
'..\Shared\Strings\en-US\Resources.resw' produced
'namespace RootNamespace....Shared.Strings', which does not compile. The
paths are resolved before being compared, and such a resource now takes the
root namespace of the project, which is what makes sharing one possible at
all.

Also drop HtmlStringSamplePage, which binds an attached property that no
longer exists anywhere in the repository. It was excluded from the project
and had not been built for a long time; sharing the pages by folder rather
than by list is what surfaced it.

Add a Native AOT UWP sample beside the .NET Native one
The support added in the previous commit had nothing exercising it: both
existing UWP samples are .NET Native projects, which are recognized by the
API contract reference and never take the UseUwp path.

Add a second UWP sample built on modern .NET with Native AOT, beside the
existing one rather than in place of it, so the two toolchains are shown
side by side. It is deliberately a single page: it shows a strongly typed
property, a generated formatting method, pluralization with its empty
state, and the generated markup extension, without duplicating the nine
pages of the .NET Native sample. The images are shared with that sample
rather than copied.

Two things this sample surfaced, both worth having in a sample:

  - a UWP project on modern .NET does not pick .resw files up on its own,
    so they have to be declared as PRIResource, which is also what hands
    them to the generator;
  - a Page already has a Resources property, so the generated class has to
    be aliased to be read from a page.

Recognize a UWP project built for Native AOT
A UWP project is recognized by the Windows.Foundation.UniversalApiContract
reference it carries. A UWP project built for Native AOT has the UWP types
available but no reference of that name, so it looked like no supported app
type at all: it was reported as RESWP0005 and got no code, with nothing
pointing at what to do about it.

Read the standard UseUwp property such a project already sets, and trust it
over the references: declaring what the project is outright is better
evidence than a reference happening to be named a certain way.

This is the change proposed in #48, carried over to the pipeline the
generator has since been split into and covered by tests, including the
state it fixes -- what a Native AOT UWP project used to get -- so the
regression is pinned rather than described.

Also expose ProjectDir and ProjectTypeGuids, which the generator has always
read but which the targets never made visible to it, so the fallbacks that
depend on them could never fire.
